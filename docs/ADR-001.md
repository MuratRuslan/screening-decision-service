# ADR-001: Reliability mechanisms for the cv.parsed → decision → screening.decision.created pipeline

## Status

Accepted.

## Context

`screening-decision-service` sits between two Kafka topics: it consumes `cv.parsed` and
must publish exactly the right number of `screening.decision.created` events (zero for
duplicates, one otherwise), even though:

- The consumer may run with multiple replicas reading the same partitions (well, the same
  topic across replicas in the same consumer group — each partition assigned to one
  replica at a time, but replicas can change on rebalance).
- A crash can happen at any point: after the DB commit but before the Kafka publish, mid-
  publish, or between polling the outbox and marking it sent.
- A manual override (`PATCH /decisions/{id}/override`) can race with another override of
  the same decision.
- An invalid or malformed event must not stop the consumer from processing the next
  message on the partition.

This ADR records the decisions made to handle all four, and the trade-offs accepted.

## Decision 1: Transactional outbox, not dual-write or CDC

**Chosen:** decision + `CREATED` audit row + `NEW` outbox row are written in one DB
transaction (`DecisionPersistenceService.persist`, `@Transactional`). A separate
`OutboxPublisher` polls `outbox_events` and publishes to Kafka, marking rows `SENT` after a
successful send.

**Alternatives considered:**
- *Dual write* (save to DB, then publish to Kafka, no outbox table) — rejected outright:
  if the process crashes between the two writes, the event is either lost or duplicated
  with no recovery mechanism. This is the exact failure mode TASK.md calls out
  ("надёжно, без потери при сбое между БД и Kafka").
- *CDC-based outbox* (e.g. Debezium tailing the Postgres WAL) — gives the same guarantees
  with less application code, but requires standing up and operating a CDC pipeline
  (Kafka Connect, a connector, WAL replication slots) that is disproportionate
  infrastructure for this task's scope. Rejected for now; noted as the natural next step
  if this were a real production service.

**Consequence:** delivery is **at-least-once**, not exactly-once — see Decision 3.

## Decision 2: Idempotency via a DB unique constraint + insert-and-catch, not exists-then-insert

**Chosen:** `screening_decisions(candidate_id, parsed_at)` is a unique constraint (Flyway
`V2`). `DecisionPersistenceService.persist` inserts the decision and calls
`decisionRepository.flush()` immediately, forcing the constraint check to happen inside the
method rather than lazily at some later flush point. The **caller**
(`DecisionProcessingService.process`, which is *not* itself `@Transactional`) catches the
resulting `DataIntegrityViolationException`, logs "duplicate ignored", and returns — no
audit row, no outbox row, no error propagated to the Kafka error handler.

**Why not `existsByCandidateIdAndParsedAt()` then insert?** That has a race window: two
replicas (or two threads) can both check "does this exist?", both get `false`, and both
proceed to insert — the exists-check is not atomic with the insert. Only the database's own
uniqueness enforcement is atomic across concurrent transactions. This is *the* mechanism
that makes the consumer safe with multiple replicas — application-level locking or
distributed locks were considered and rejected as unnecessary complexity when Postgres
already provides this guarantee for free.

**Why the separate `DecisionPersistenceService` bean instead of a method on
`DecisionProcessingService`?** Self-invocation (a bean calling `@Transactional` methods on
itself) bypasses the Spring AOP proxy, silently running the method *without* a transaction.
Splitting persistence into its own bean, called from a different bean, guarantees the
transactional advice actually applies.

## Decision 3: At-least-once outbox delivery is accepted, not engineered away

**Chosen:** `OutboxPublisher.publishBatch()` claims a batch with a native
`SELECT ... FOR UPDATE SKIP LOCKED` query and — this is the specific design point worth
recording — sends each claimed row **inside the same transaction that claimed it**, rather
than in a separate `REQUIRES_NEW` transaction per row.

**Why not split claim and send into separate transactions (a "claim → mark SENDING →
commit → send → mark SENT/retry → commit" two-phase flow)?** That's the more "textbook"
outbox-publisher design, and was considered. It was rejected here because, without a
reaper process to un-stick rows that crash while `SENDING`, it trades one failure mode
(at-least-once delivery) for another (a row stuck in `SENDING` forever after a crash mid-
send) — and building the reaper is exactly the kind of scope this task's time budget
doesn't have room for. It also was **not** replaced with "claim in one transaction, send in
a nested `REQUIRES_NEW` transaction per row" (an intermediate option) — that specific
combination is actually broken: the claiming transaction's `FOR UPDATE` locks are held
until *it* commits, so a `REQUIRES_NEW` transaction on a different physical connection
trying to `UPDATE` those same rows would block waiting for a lock the outer transaction
won't release until the inner one finishes — a self-inflicted deadlock/stall, not a
correctness improvement.

**Consequence, accepted:** a crash between the Kafka broker's ack and this transaction's
commit leaves the outbox row `NEW`, so the next poll re-sends it — genuine at-least-once,
not exactly-once, delivery. The outbound `DecisionCreatedEvent.eventId` is a fresh UUID
per *send attempt* at the domain-event level but is stable per *decision* in the sense that
retried sends carry the same decision id — a downstream consumer that dedupes on
`decisionId` (or on `(candidateId, parsedAt)`, mirroring our own idempotency key) is
protected. This is called out explicitly rather than claiming a false exactly-once
guarantee.

**Bonus items this design happens to satisfy cheaply:** `FOR UPDATE SKIP LOCKED` (multi-
instance-safe outbox polling), batched publish (`app.outbox.batch-size`) with backpressure
(non-overlapping `fixedDelay` scheduling — a slow Kafka broker naturally throttles the poll
rate instead of piling up concurrent batches).

## Decision 4: Dual optimistic-concurrency check for manual override

**Chosen:** `PATCH /decisions/{id}/override` (`DecisionOverrideService.override`) checks
version twice:

1. An explicit comparison: load the entity, compare `entity.getVersion()` to the
   `expectedVersion` header. Mismatch → `VersionConflictException` with the exact
   contract-format message ("Ожидалась версия X, текущая версия Y").
2. JPA's own `@Version` column on `ScreeningDecisionEntity`. Hibernate's dirty-checking
   issues `UPDATE ... WHERE id = ? AND version = ?` at commit; if another transaction
   already bumped the version between step 1's read and this commit, zero rows match and
   Hibernate throws `ObjectOptimisticLockingFailureException`, mapped by
   `GlobalExceptionHandler` to the same `409 VERSION_CONFLICT`.

**Why both?** Step 1 alone has a TOCTOU (time-of-check-to-time-of-use) gap: two requests
can both read the same version, both pass the check, and both proceed to write — only the
second one to actually commit should win, and only the real DB-level compare-and-swap
(step 2) can guarantee that. Step 1 alone is what gives the *friendly, contract-exact*
error message for the overwhelmingly common case (a client working from a stale read);
step 2 alone would still be correct but would surface a generic optimistic-lock exception
for that common case instead of the documented message format. Together they're both
correct and give the better message where it matters most.

`ScreeningDecisionEntity.version` intentionally serves both roles at once (the contract's
`expectedVersion` token *and* JPA's optimistic-lock column) rather than maintaining two
separate counters — they need to agree in this design, since the contract's version
semantics ("increment on each manual change") is exactly what JPA's `@Version` already
does for us on every managed-entity update.

## Decision 5: Retry classification and DLQ funnel

**Chosen:** `NonRetryableEventException` (malformed JSON, JSON Schema violations, unknown
active rule-set, and optionally unknown criterion keys under the `DLQ` semantic-catalog
policy) is registered with Spring Kafka's `DefaultErrorHandler` via
`addNotRetryableExceptions`, so these skip retries entirely. Everything else retries with
`ExponentialBackOff`, bounded by `max-elapsed-time-ms`, before falling through to recovery.
Both the immediate-non-retryable path and the retries-exhausted path are handled by the
same `DlqPublishingRecoverer`, so `screening.decision.dlq` always has one envelope shape
regardless of which path produced it, and a bad message can never stall the partition for
subsequent messages (the container commits past it either way once the recoverer runs).

## Consequences summary

| Property | Guarantee |
|---|---|
| Duplicate `cv.parsed` (same candidateId+parsedAt) | Exactly one decision, exactly one outbound event |
| `screening.decision.created` delivery | At-least-once (documented, not exactly-once) |
| Consumer replicas | Safe — idempotency is DB-constraint-driven, not in-memory |
| Outbox publisher instances | Safe — `SKIP LOCKED` gives each instance a disjoint batch |
| Concurrent `PATCH /override` on the same decision | Exactly one wins; the other gets `409 VERSION_CONFLICT` |
| Invalid/malformed `cv.parsed` event | Routed to DLQ with diagnostics; next message unaffected |

## Recorded ambiguities (per TASK.md's request to document unresolved contract questions)

- `AuditAction.UPDATED_BY_REPLAY` is defined in the contract but no current requirement
  produces it; reserved for a future recompute endpoint, never emitted today.
- `GET /decisions/by-candidate/{candidateId}` returns the decision with the greatest
  `decided_at` for that candidate — chosen because a candidate can legitimately have
  multiple decisions across different `parsedAt` re-screenings.
- Unknown semantic-catalog criterion keys default to the `AUDIT` policy (recorded, not
  rejected) rather than `DLQ`, on the reasoning that one unrecognized criterion in an
  otherwise-valid event shouldn't block an entire screening; this is configurable via
  `app.semantic.unknown-key-policy` for deployments that want the stricter behavior.
